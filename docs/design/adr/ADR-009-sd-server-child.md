# ADR-009：画像生成は sd-server（stable-diffusion.cpp）を子プロセスで動かす
- 状態：承認 ／ 日付：2026-11-06 ／ 決定者：ユーザー（チャットのスレッド内・300 秒・チャットを止める）＋ Claude 判断（sd-server を選ぶ点）
- 影響する ID：REQ-001, FR-012, API-095〜096, D-71, D-72

## 状況
画像モデル（SD 1.x・SDXL の単一ファイル）を DL しても、今は保存するだけで使えない（D-71）。アプリ内で画像を生成したい。ADR-002 と同じく、配布は公式ビルドの同梱・子プロセス・Python なし・Windows（CUDA / Vulkan / CPU）で動かしたい。

## 決定
leejet/stable-diffusion.cpp の `sd-server` を同梱し、worker が子プロセスとして起動する。画像モデルは起動引数 `-m <ファイル>` で読み込み、1つだけ常駐させる。生成は `POST /sdcpp/v1/img_gen`（非同期ジョブ）→ `GET /sdcpp/v1/jobs/{id}` で待つ。時間を過ぎたら `POST /sdcpp/v1/jobs/{id}/cancel`。

画像モデルを読むときは、チャットの llama-server を止める。逆にチャットを読むときは sd-server を止める（`EngineManager` の読み込み前の処理）。

## 代替案
| 案 | 良い点 | 悪い点 | 不採用の理由 |
|---|---|---|---|
| sd CLI を生成ごとに起動 | 常駐の管理が要らない | 生成のたびにモデルを読み直す | 読み直しが毎回数十秒かかる |
| ComfyUI など Python のサーバー | 対応モデルが多い | 配布物が数 GB。Python が要る | ADR-002 の「Python なし」に反する |
| node で拡散モデルを直接動かす | 子プロセスが減る | ネイティブの GPU 対応を自前で作る | 版上げの負担が大きい |

## 影響
- sd-server は `--api-key` を持たない。待受は 127.0.0.1 だけに限り、ポートは毎回空きを取る（D-60 と同じ扱い）
- 対応は単一ファイルのチェックポイント（SD 1.x・SDXL など）。FLUX・SD3 のように複数ファイルが要るモデルは v1 では対象外（レシピと部品の指定が要る）
- 同時に常駐するのは1つ（チャットか画像）。切り替えには数十秒かかる（ADR-002 と同じ）
- Windows では `sd-server.exe` を `LLM_PARTY_SD_BIN` で指す。PID の後始末は既存と同じく `/proc` を見るので、Windows では強い保証はない（ADR-002 と同じ限界）
- 実機での生成は未確認（開発機で偽のバイナリを使ったテストのみ）。実際の sd-server での確認が残る
