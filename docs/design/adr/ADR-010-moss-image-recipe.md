# ADR-010：MOSS-Image は部品のレシピとして複数ファイルで動かす
- 状態：承認 ／ 日付：2026-11-06 ／ 決定者：ユーザー（対象は MOSS のみ・部品は一括・エンコーダは Qwen3.5-9B 系・書き換えは今回なし）＋ Claude 判断（既定の部品の版）
- 影響する ID：FR-012, API-097〜098, D-72, D-73, ADR-009

## 状況
MOSS-Image は DiT・テキストエンコーダ（Qwen3.5-9B 系）・VAE・トークナイザの4つを要る。D-72 の画像モデルは単一の `.safetensors` の前提なので、このままでは動かない。unsloth の model card の sd-cli 例（手順として検証されたもの）は `--diffusion-model` `--llm` `--vae` `--tokenizer` を指定する。

## 決定
MOSS-Image を「レシピ」として持つ。レシピは部品のファイル名と取得元の固定の一覧で、アプリが一括で DL する。DL が終わると画像モデル（`use: image`）が1つ登録され、部品の場所をモデルの記録に持つ。sd-server は `-m` の代わりに部品のパスを渡して読む。

## 代替案
| 案 | 良い点 | 悪い点 | 不採用の理由 |
|---|---|---|---|
| 利用者が部品を1つずつ選ぶ | 部品の差し替えが自由 | 組み合わせの誤りが増え、画面が複雑になる | 最初の目的は「入れて生成」 |
| ComfyUI を子プロセスで動かす | 対応モデルが多い | Python が要る | ADR-009 で退けた |
| FLUX・SD3 も一般化する | 将来の対応が広い | 検証の範囲が大きい | 利用者が MOSS のみを選んだ |

## 影響
- 同梱の sd-server を master-975 以降に上げる。版ずれのリスクは R-17
- DL の空き容量は部品の合計＋2GB（D-31）。既定の組み合わせはエンコーダだけで約 9GB 級のため、8GB の GPU には載らない見込み（R-18）
- 実機の生成は未確認。根拠は unsloth の model card と、検索で見つけた二次情報（stable-diffusion.cpp の対応）
